## Unreleased

### Added

- The print preview gains **zoom presets** (dot grid / fit / 100% / 200% / 400%), defaulting to the dot-grid tier whenever the template sets `printerDpi`: one screen pixel per print dot (≈2.11× at 203 dpi). Trigger: "bars run together" in the preview. At true CSS size a 95 mm sheet is only 359 screen pixels, so a 74.32 mm / 297-module code collapses into 281 pixels (0.945 px per module) — the paper's 2 dots per module cannot fit in 1 screen pixel, narrow bars round to 1 or 2 px and gaps to 1 px (measured 73 distinguishable bars versus 76 on paper). **This is not anti-aliasing** — grey pixels are already 0.0% under `crispEdges`. On the dot-grid tier bar widths land exactly on 2/4/6/8 px, matching the paper point by point. The zoom is written into a guard style inside the preview iframe with `@media print{zoom:1}`, so it never enters the rendered artifact or pagination (the barcode measures 281 px again under print media); the template contract is unchanged (`printerDpi` is read-only)
- **New elements default to Heiti; the font dropdown gains a "local system fonts" tier** (trigger: thermal users reporting that saving the same template as a PDF and printing it gives sharper text than printing straight from the browser. Both routes consume the identical core HTML with the same `@page` and `paperMm`; once scaling and font loading were ruled out, the cause is Chromium's own print backend submitting glyphs without device-grid fitting — an external pipeline, so the fix belongs on the design side). Single source in core's `print/fonts.ts`: `DEFAULT_PRINT_FONT_FAMILY = 'SimHei'`, `SYSTEM_FONT_OPTIONS` (installed fonts needing no font file — `SimHei` / `Heiti SC` / `Hiragino Sans GB` / `Noto Sans CJK SC` / `Microsoft YaHei` / `PingFang SC` / `SimSun` / `KaiTi` / `FangSong` — each label stating "thermal pick / screen-tuned / use with care on thermal"), and `withSystemFontOptions` (host-declared @font-face fonts first, system tiers after, host winning on name clashes). Rollout: `createDefaultOptions` stamps the default family on **every new element**, tables additionally carry the new `tableDefaultFontFamily`, and cells resolve in the order *cell → table default → CSS inherit*, in sync between the print path (`matrixCellStyle`) and both canvas shells; both hosts (canvas `TableSettingsGroup`, print-common `tableSettingsGroup`) gained a "默认字体" selector. **Weight stays `normal`**: asking for `bold` without a matching weight file makes Chromium synthesise bold, and the metric drift silently reflows pagination (a warning already recorded in `print/fonts.ts`) — Heiti is already heavier than YaHei, so no fake bold. **Existing templates are byte-identical**: with `fontFamily` unset the print path still emits no declaration; only new elements pick up the default. One real defect fixed along the way: the canvas wrote the bare family name (`fontFamily || 'inherit'`), so a machine missing that font fell back to the UA default while print used the fallback stack — two different faces on screen and on paper; both now share core's new `resolveCanvasFontFamily`. **Cross-target caveat**: system fonts resolve differently per target (canvas, browser print and the desktop client use whatever the user machine has; server PDFs use the render container, whose only CJK font is `fonts-noto-cjk`); missing names degrade gracefully through the fallback stack rather than showing tofu, but the metric change can shift wrapping and pagination — for byte-exact cross-target output keep using template font declarations, and note that **SimHei and Microsoft YaHei are Microsoft-licensed and must not be redistributed inside images or installers** (Noto / Source Han are OFL). The `print-template-json` skill is updated in step: `build_template.py` stamps the same default at build time (a table's `family` shorthand maps to `tableDefaultFontFamily`) and `references/template-schema.md` adds a "字体档位" section.
- **Barcode bar height** `barHeight` (property panel → 条码设置 → "条高 (mm)"): available on both the barcode **element** and **table cells**, kept in sync across the four surfaces (canvas + print-common, element panel + cell panel). Measured in millimetres and covers **the bars only — the human-readable text underneath is excluded**. The hard rule is *bar width wins*: the requested height is converted through the per-module width, so it can only land on a whole multiple of it (0.5 mm steps at `barWidth: 4`), and when the available box is too short the bar height gives way rather than squeezing the bar width (a non-integer X-dimension is exactly the "uneven bars" defect this module exists to prevent). Why two render passes: the per-module width is `box width ÷ module count`, the module count is only known after the SVG is produced, and the bar height needs that width to be converted — so the first pass runs at the default 30 modules to learn the module count and the measured text-area occupancy, and a second pass redraws at the target height only when needed. **Templates that leave `barHeight` unset, or whose conversion lands on the default band, still render in one pass and stay byte-identical on paper.** Measured baseline (56.4 × 14.1 mm box, 8 digits in CODE128C = 99 modules, `barWidth: 2` → 0.25 mm/module): asking for 20 mm exceeds the box, so the bar area converges to 66 modules and the whole graphic to 80 modules = exactly 20 mm, with the bar width untouched at 0.25 mm. If the text area alone fills the box, the bar area falls back to 1 module so the code never disappears entirely. The note hangs on `button.pd-help` (single source: core's `PROPERTY_REGISTRY` key `cd-bar-height`); property search matches 条高 / 条码高度 / 条区高度. **Unlike "最大高度 (mm)"**, which caps the whole graphic including the text, this field governs the bar area only.
- **Barcode quiet zone** `barQuietZone` (property panel → "条码设置" → "静区 (模块)"): available on both the barcode **element** and **table cells**, kept in sync across the four surfaces (canvas + print-common, element panel + cell panel). Measured in modules (1 module = 1 bar width) and applied left/right only (top/bottom padding would eat element height); range 0–20, **default 10** — 10 is exactly the floor the 1D symbologies demand (GS1: the greater of 2.54 mm and 10× the X-dimension), which is why the default is not 0 like the QR one. Smaller means thinner white edges and thicker bars in the same box: an 8-digit CODE128C is 99 modules wide of which 20 are quiet zone, so with `barQuietZone: 0` a 20 mm box goes from 0.202 mm to 0.25 mm per module (+23.7 %). **The default keeps existing templates byte-identical.** With 0 the quiet zone disappears and, since it participates in the bar-space-bar transition, scannability can break next to text or table rules — verify on paper. The QR quiet zone stays a separate `qrQuietZone` (default 0).
- **Bar width multiplier upper bound raised from 4 to 8**: the preferred module width can now reach `8/2 × 0.25 mm = 1 mm` (twice as large when the box allows); with `printerDpi` set it still snaps to whole print dots. The settlement rule is unchanged — it still only scales down, never up — so "the barcode stops growing inside a big box" is governed by this cap, which has now doubled.

### Fixed

- **Table cells dropped `barWidth` / `barFontSize` on the print path**: `data-binder` enumerates cell fields one by one, and neither was listed nor declared on `RenderCell`, so raising the bar width only grew the barcode in the designer while paper kept the default 0.25 mm/module (the same trap as `qrQuietZone` and `objectPosition`). Both fields are now carried through, so design view and output share one geometry again.
- **Cell barcodes read the wrong font-size field**: output used the cell body `fontSize` (pt) while the panel writes `barFontSize` (relative to the 30-module bar height), diverging from canvas `CellBarcode`. It now resolves `barFontSize ?? fontSize` (barcode elements only have `fontSize`, so that path is byte-identical). **Existing impact**: only for a barcode cell that sets `fontSize` without `barFontSize`, the text area returns to the default band and the barcode scales slightly with it — this pulls the output back to what the designer shows.

## V1.3.8(2026-10-22)

### Added

- **Visual crop positioning** ([GitHub issue #4](https://github.com/worm-longliu/worm-vue3-print/issues/4)): the image property panel now offers a position preset, numeric fields for the movable axes, and an original-image window — the red box is exactly the area that will print, moving as presets or numbers change. When the natural size is known, only axes with real travel are shown (the 3×3 grid appears only when both axes move); without a size it falls back to two fields. Legacy values that cannot be normalized (mm offsets, four-value syntax, `calc`) open as "Custom" and are preserved verbatim. The user-facing name of `cover` is now 剪裁（等比铺满后裁边）; the option table lives once in core and both canvas and print-common consume it.
- **Crop zoom `fitScale`** (100–400, consumed only by 剪裁): a picture that matches the frame's ratio fills the frame exactly under `cover`, leaving no edge to crop; the zoom percentage pushes the picture larger so both axes gain a croppable edge. Declarations come from the new core module `render/crop-style.ts` and are shared by the paper renderer, canvas and print-common. `transform: scale()` takes its origin from the same anchor value (the anchor is both the pinned point and the zoom origin). 100 and the default emit nothing; existing templates stay byte-identical.

### Changed

- **The anchor block appears only for 剪裁**: 包含 / 拉伸填满 / 原始尺寸 / 缩小 no longer show crop anchor or zoom rows — those modes have no cropped edge, and with a square frame holding a square image the row only said "no travel on either axis". Both element panels and both cell panels now share this gate.
- **Table image cells in 剪裁 no longer stretch the row on paper**: `cover` pins the outer box to the available height and makes the `<img>` fill it; measured in real Chromium, a declared 12mm row drops from about 23.8mm back to 12mm, and top/bottom anchors really crop (top anchor prints the top red band, bottom anchor the bottom blue band). The other four modes are unchanged. **Note**: existing templates that use 剪裁 in table image cells will print with shorter rows; please re-check the layout.

### Fixed

- **Ten-thousands / hundred-millions units lost in uppercase amounts** ([Gitee #IKOYG0](https://gitee.com/liulong_oschina/worm-vue3-print/issues/IKOYG0)): the old four-digit grouping took the unit from the current group index, which is still 0 when the first group is full, so 万 / 亿 never appeared. The implementation now concatenates groups from the most significant down, takes the unit from each group, and fills zeros across groups; it also fixes the required 零 after 元 when the jiao digit is 0 but the fen digit is not, and keeps the 元 placeholder for amounts below one yuan. Only three output classes change (≥10,000, x.0y yuan, 0<|amount|<1), all from wrong to correct.
- **Font dropdown no longer distorts the host** ([Gitee #IKP3MU](https://gitee.com/liulong_oschina/worm-vue3-print/issues/IKP3MU)): the candidate list used to stay in flow, growing the top-bar unit from 28px to 157px and pushing the property panel down by 122px; it is now an overlay that flips up or down based on available space, so the top bar, the More panel and the property panel stay put. The defect dates back to the 1.3.3 merge of the format toolbar into the top bar and is not a regression of the 1.3.7 toolbar overflow.
- **Single-page templates with rules and a table were split into two pages** ([Gitee #IKOUJI](https://gitee.com/liulong_oschina/worm-vue3-print/issues/IKOUJI), C3): pagination used to accumulate a one-dimensional vertical budget, so vertical lines that do not intersect the table still consumed it and forced a false page break; after the break elements switched to a flow cursor and lost their design coordinates. The budget is now accounted per horizontal occupied column, so rules and the table each use their own column; the reporter's template goes from 2 pages with the horizontal rule at page 2 y=38.9 back to 1 page at y=86.8 (design 86.87). **Scope**: C2 (data-driven drift of the table follow area) and C1 (missing height of vertical lines inside the follow area) remain open in the same issue and are tracked as TODO T-11; this release does not claim the whole issue is closed.
- **Unevaluated image expressions in design mode** (e.g. `{image}`) are no longer treated as real images: the panel falls back to the built-in sample and labels it, and a changed or failed image clears the previous travel/window instead of showing "broken image + stale travel". The preview frame geometry that stretched into a wide rectangle is fixed as well (the red box now shares the sample image's frame).
- **Long field keys pushed the CJK label out of the material panel** ([Gitee #IKPAGV](https://gitee.com/liulong_oschina/worm-vue3-print/issues/IKPAGV)): a field row used to keep 中文名 and 变量名 on one line with the key unlimited, so a long key squeezed the label to 0px and overflowed the 224px sidebar itself. The row now wraps adaptively — one line while both fit, otherwise the key drops to a second line and the label takes the full width; each side ellipsizes when still too long, and hovering the row shows the full "label (key)", group headers get the same tooltip. Canvas and print-common share the structure and rules; measured on a long field the label renders 148px wide in full, while all 14 original demo fields stay on one line at 33px.

## V1.3.7(2026-10-19)

### Added

- The four demo-common hosts (jquery / vue2 / react / vue3) now share the same adaptive top-bar overflow (T-10 of [GitHub issue #4](https://github.com/worm-longliu/worm-vue3-print/issues/4)): each gains its own `topbar-overflow.js` (same rule as core `resolveToolbarOverflow`, re-implemented because these hosts have no bundler access to the core subpath) plus `topbar-overflow.css`, since `demo-ui.css` is a generated artifact that must not be hand-edited. Measured on all four hosts at 1600/1280/900/700/640: zero wrapped labels, zero content bleeding below the bar, constant 45px bar, 0/0/3/5/8 units collapsed; a checkbox relocated into the panel still reacts to framework state (class gains `on`, label reads 3 份) and stays put.

- **`justify` alignment** ([GitHub issue #4](https://github.com/worm-longliu/worm-vue3-print/issues/4)): added to `TextAlign`, with a 两端 radio and a 4th toolbar cell (`TextAlignJustify` in both canvas and print-common). Two renderer fixes keep all three ends in sync: combined with vertical alignment the flex main axis switches to `column` so the line box spans the full width (an anonymous flex item of a row container cannot stretch, which silently degraded `justify` to left alignment), and `text-align:justify` is now paired with `text-align-last:justify` — CSS never justifies the last line of a paragraph, and a text element usually has exactly one line, so `justify` did nothing at all before (measured in the live designer: 140px line box inside a 349px element, now full 349px). Following other print designers, `justify` here means "fill the line width, last line included"; in Word that form is called distributed alignment.
- **`justify` for table cells**: the cell property panel gained a 4th option 两端 in canvas and print-common. The toolbar's justify button already wrote `align: 'justify'` in cell context (`useFormatToolbar` reuses the same panel when `context === 'cells'`), but the property panel neither showed nor offered it and the renderer emitted only `text-align:justify` — measured live, content in an 83px header cell stayed at 48px. Core `matrixCellStyle()` now pairs it with `text-align-last:justify` and canvas `TableElement` / print-common `table.ts` mirror that at design time, so the same cell fills its 73px content box. Defaults remain `left`/`center`; existing templates are unchanged unless a cell carries `justify`.
- **First-line indent reaches paper** (the 外观 group now exposes 首行缩进 (字符) with its tip): `longTextIndent` emits `text-indent` in **em** (follows the font size, including under `textFit='shrink'`), matching the Word/WPS "indent 2 characters" convention; canvas and print-common moved from `pt` to `em`. Only `longText` consumes it.
- **`objectPosition` crop anchor**: emitted for standalone images and table image cells; the 外观 group gained 缩放模式 / 裁剪锚点 controls for images (table image cells get 裁剪锚点 in the cell panel too) (identical placement and copy in canvas and print-common, tips sourced from core `PROPERTY_REGISTRY`). Values with `;`, quotes or `url()` are dropped wholesale (host CSSOM drops them the same way).

- Desktop client, printing path: **direct HTML printing**. The final HTML produced by the core pipeline goes straight into `webContents.print({ silent: true })`, the same route the browser's `window.print()` uses: paper is declared explicitly in **micrometers** from the `paperMm` the pipeline computed, margins are always `none`, and `deviceName/pageSize/copies/landscape` are logged before the job is submitted (`Chromium 原生打印参数`). No external command is needed on any platform. The paired `printToPDF` output is generated only when **Keep generated PDF** is enabled, as a comparison **reference** (otherwise rendering stops at the preparation stage); job records now carry a `printRoute` field (older entries are to be read as `pdf`). Measured on macOS against a label queue that supports custom sizes: the printed medium matches the declared size exactly (60×40 / 80×60 / 100×80 mm, `/Rotate=0`, content upright), which is tighter than the rounded `printToPDF` result on the PDF route (60.4×40.2 mm); `silent` raised no dialog and the 60s callback fallback never triggered.

- Designer toolbar: **adaptive overflow menu**. When the row cannot fit every button group, groups collapse into a new "更多 / More" dropdown following a fixed priority chain (clipboard → format painter → zoom → arrange/view → borders → colour → align → text style → font & size), keeping the original group titles and icon grids inside the panel; if everything is collapsed and it still does not fit, the brand text falls back to ellipsis truncation. The decision function `resolveToolbarOverflow` lives in `@worm-vue3-print/core/designer`, so both hosts (canvas and print-common) share one chain. The canvas host relocates groups with `Teleport`, so component instances are never remounted and the border panel's chosen line style / width / colour survive repeated window resizing.

- Demo top bar: same adaptive overflow. The project mark, title and "打印输出" stay resident; the other 9 items collapse into a "更多" panel in the order template ID → business type → host switcher → clear → import → export → custom fields → batch print → load sample. Before the change, at 640px the 45px bar pushed the "自定义字段与数据" button to 156px tall (characters stacked vertically) with all 11 text items wrapping and 55px of bleed below the bar; after it everything fits with nothing stacked or overflowing. The left/right split now uses an explicit `.demo-spacer`, because `.demo-print-btn:first-of-type { margin-left: auto }` stopped matching once the buttons were wrapped into overflow units.

- The overflow mechanism became a public canvas API: `provideToolbarOverflow`, `useToolbarOverflow`, `emptyToolbarOverflow`, `createOverflowUnitDirective`, `TOOLBAR_OVERFLOW`, plus the `ToolbarOverflowContext` / `OverflowUnitDef` types. Drop-in targets are now matched by the `data-overflow-slot` attribute and the natural-width exclusions by `data-overflow-more` / `data-overflow-spacer`, so hosts no longer have to reuse canvas class names.

- Desktop client: the window and tray icons use the same `build/icon.png` as the installer (the image now ships inside the asar, about +1 MB per installer), so the taskbar, Alt-Tab and shortcuts all match; macOS keeps the monochrome template tray icon so the menu bar can invert for light/dark.
- The property panel gained **Quiet zone (modules)** for QR codes ([Gitee issue #IKN95F](https://gitee.com/liulong_oschina/worm-vue3-print/issues/IKN95F)) — available on both the QR code **element** and **table cells**, with the same behaviour in the canvas and print-common hosts. Range 0–8; the default is **0** modules (the print side used to hard-code 4, so existing templates now paint the code face across the whole box instead of 72.4%). At 0 there is no white band at all and the code face fills the box proportionally — the quiet zone scanners need is then whatever blank paper surrounds the box. Enter 4 to return to the ISO/IEC 18004 recommended quiet zone. Searching "静区 / white band / quiet" finds the field. The explanation lives on a help icon after the label (revealed on hover or click, with the wording kept in a single source in the core property registry) instead of a permanently visible hint line.
- **`@worm-vue3-print/common` is now published to npm as a preview.** Until now the package was only built inside the workspace, so non-Vue3 hosts had to install from source. It is released as a **prerelease**: dist-tag `next`, version `1.3.7-beta.0`, **not `latest`** — the install line has to be `npm i @worm-vue3-print/common@next @worm-vue3-print/core` (there is no `latest` yet, so omitting `@next` fails with `No matching version found`). The stylesheet also gained a public subpath, `@worm-vue3-print/common/style.css` (→ `dist/common.css`, needed only when the designer renders into the light DOM; `exports` previously exposed `.` and `./browser` only, so bundlers could not reach that CSS). Publishing stays **out of GitHub Actions** and runs from local scripts: `npm run publish:common:dry-run` to rehearse, `npm run publish:common:beta` to publish (builds core → canvas → common in that fixed order, then runs the core / canvas / common suites; the dry run exits 0 with a 43-file / 380.0 kB tarball, 1.3 MB unpacked). Steps and guardrails are in `CONTRIBUTING.md`, "Method 3". **The package is still experimental and has not passed stability testing — not recommended for production**; Vue 3 hosts should keep using `@worm-vue3-print/canvas`.

### Fixed

- Desktop client: **templates containing a barcode or a QR code could not print at all** — every such job ended in `PRINT_FAILED: 码值渲染超过 ~30000ms` (code-free templates were unaffected). The pipeline generates code SVGs in the page *before* the first `setContent`, and the Electron driver called `webContents.executeJavaScript` on a window that had never committed a document; Electron queues the script waiting for a navigation that never arrives, so the call hung silently until the budget expired. The driver now loads a blank document before the first executor injection. Measured against a local PDFwriter queue: the shipped waybill template (barcode + QR on 100×150 mm custom paper) went from timeout to **2.5 s**, with the spooled media exactly 100.00×150.00 mm and `/Rotate=0`; barcode-only 1.5 s, QR-only with quiet zone 4 at 1.5 s, and the typography probe template 1.9 s. **The defect dates back to 1.3.5** (the 1.3.5 client installed on the same machine times out on the same template — verified side by side); it was not introduced by V1.3.7 but ships fixed in this release. Until now those users had to fall back to browser printing or the server PDF service.
- The host-switch dropdown in the sub-demos was always painted (the author rule `display:flex` overrode the UA hiding of a closed `details`) and covered the canvas. Each host sheet now hides it again while closed; the root fix belongs in the demo style source followed by `npm run styles:demo-common`.
- Field help bubbles differed between canvas and the common host: the bare `[data-tip]::after` rule in canvas `DesignerToolbar.vue` (`bottom:-32px; left:50%; translateX(-50%); padding:4px 8px; white-space:nowrap; z-index:100`) lost its `[data-v-*]` scope while styles were derived for print-common and then also matched `.pd-help::after` in the property panel — the 90-plus-character quiet-zone note stopped wrapping, stretched into one wide strip, shifted to centre and dropped below other layers. `scope-patches.css` now restores every affected declaration from `native-controls.css`. A/B on an identical probe: both hosts report `left:0 / transform:none / padding:5px 7px / white-space:normal / width:196px / z-index:120`, with `top` off by 1px only because the `.pd-label` line box already differs by ±1px between hosts (a documented parity tolerance).

The print-common panel is naturally 282px wide, so the rule is a no-op there.

- The standalone image `fit` was hardcoded to `object-fit:contain` in print output while the canvas honoured `fit`; it now reads `opts.fit` and stays `contain` when unset, so existing templates are byte-identical.
- Theme-token wiring: inputs, chips, `.pd-dialog`, the expression editor (nav tabs, hover, preview error, four help cards), `TableContextMenu`, `PresetColorPicker` trigger/panel and all three scrollbar shades now use `var(--pd-*, original)`; 26 new tokens registered once in `.designer-container`. Light rendering is pixel-identical (browser-verified) and `.pd-switch::after` keeps its white knob on purpose.
- `PresetColorPicker`'s fragment root no longer warns about extraneous `class` (`inheritAttrs: false` + `v-bind="$attrs"` on the trigger); `.page-bg-picker` layout moved onto a real element because a fragment root never receives the host scoped attribute.

- Desktop client (macOS): **landscape labels were printed rotated onto a portrait medium on the fallback PDF printing route**. The V1.3.6 entry claiming that `-o orientation-requested=4` is implemented by **swapping the medium's width and height** — and therefore that macOS `Custom.` sizes must be declared in portrait order (short×long) — **was wrong**: that observation came from the PostScript route (`cgpdftops`) `do_rotate` logs, whereas queues that take PDF directly (driverless / `_ib`) go through `cgpdftopdf`, whose semantics are "rotate the content to fit the medium you declared" without swapping the medium. Measured on macOS 15.7.8 + CUPS 2.3.4 with the open-source RWTS-PDFwriter virtual queue (9 paper sizes × 3 declaration shapes = 27 jobs): a 100×75 label declared as `Custom.212.6x283.46` with the orientation request landed as a **212×283pt portrait** medium with the content rotated 90°; declaring the true order `Custom.283.46x212.6` produced 100×75 mm, upright content and a byte-identical result. `Custom.` is now declared in the page's true orientation on both platforms and macOS no longer adds the orientation request for it; the orientation request is kept only for landscape pages that resolve to a **standard paper name** (`A4` / `Letter` are portrait media by definition), where the measured behaviour is unchanged (landscape content printed upright on a portrait sheet). **Behaviour change**: it only affects macOS builds that set `ACTIVE_PRINT_ROUTE` back to `pdf`; the default direct-HTML route does not consume `media=` and is unaffected. Check whether a queue accepts custom sizes with `grep -m1 CustomPageSize /etc/cups/ppd/<queue>.ppd` — when it does not, `Custom.` is still silently ignored and falls back to the driver's default paper, so labels must use a driver-defined `paperName` (available only on the PDF route).

- Designer toolbar: **labels no longer wrap and bleed onto the canvas** ([GitHub issue #4, comment 1](https://github.com/worm-longliu/worm-vue3-print/issues/4)). Button groups and their text labels were flex-shrinkable, so once the intrinsic width exceeded the available width Chinese labels wrapped character by character: the title block was squeezed to 13px wide / 62px tall, its container grew to 146px and overflowed the 50px bar by 47px over the canvas. The trigger also came much earlier than reported — wrapping starts **between 1520 and 1600 CSS px** (a 1080p/2K display at 100% zoom already hits it), not only after visibly shrinking the viewport. Flex children are now non-shrinkable (only the brand block may shrink), so the adaptive overflow menu absorbs the pressure first and ellipsis truncation is the last resort.

- QR codes **now fill their element box and table cell** ([Gitee issue #IKN95F](https://gitee.com/liulong_oschina/worm-vue3-print/issues/IKN95F)). A QR code renders through an `<img>`, but the print side only declared `max-width/max-height:100%` without `width/height:100%`, so the replaced element fell back to its intrinsic size — and that intrinsic size is "modules × 4 + a 4-module quiet zone" (116px ≈ 30.7mm for the default payload), completely unrelated to the box measured in millimetres. Any box larger than that left the code visibly undersized and made `object-fit` a no-op (measured in real Chromium: a 60mm box painted 65.3%, an 80mm box 48.9%; a 24mm box happened to be clamped exactly by `max-width`, which is why small QR codes looked fine). The print side now emits `width:100%;height:100%`, and when `fit` is unset it outputs `object-fit:contain` to match the property panel default (previously the preview wrote `contain` while the print output wrote nothing). The four design-time implementations (canvas `QrcodeElement` / `CellBarcode`, print-common `shell/code.ts` / `shell/table.ts`) now reuse the very same SVG from `@worm-vue3-print/core/browser`: canvas had been passing the millimetre number as pixels into the `qrcode` library's `toDataURL({ width })`, so a 28.2mm box produced a 28px image (measured at 26.3% of the container) with non-integer module widths; print-common used `margin: 0` for elements, `margin: 1` for cells and 4 modules for print output — three different quiet zones. **Note**: the quiet zone used to be 4 modules on paper but 1 module in the canvas preview and 0 in print-common — three different pictures for the same template. It is now driven by the new `qrQuietZone` property with a 0-module default (see Added), preview and paper always show the identical SVG, and resizing a box no longer re-renders the code.

### Added

- `@worm-vue3-print/core`: Added **barcode print-dot alignment** (new module `render/barcode-dot.ts`) — the barcode's final size is snapped to the printer's dot grid, fixing "bars come out alternately wide/narrow with gray edges" on thermal printers. Root cause (measured): with a 56.4×14.1 mm element box and an 8-digit CODE128, one module is 0.318 mm, i.e. **2.55 dots at 203 dpi (8 dots/mm)**. The barcode is pure vector and geometrically exact in the PDF, but the printer/RIP can only image whole dots, so a fractional module width is rounded to 2 or 3 dots per bar. Dedicated label tools look crisp because they define the narrow bar as a whole number of dots (e.g. 3 dots = 0.375 mm). Barcode elements accept `printerDpi` (`options.printerDpi`, typically 203/300/600), and **barcode table cells accept it too** (`TableCell.printerDpi`; the box is the cell's content area — spanned column widths / row heights minus padding and collapsed borders, derived with the new `cellFitWidthMm` plus the existing `cellFitCapMm`; when a table has no `tableColWidths` the width is unknown and alignment is skipped). - `@worm-vue3-print/core`: Fixed missing **page breaks between copies** in multi-page batch printing. Each copy was wrapped in `.print-copy`, but the composed CSS omitted the copy-break rule, so the last `.print-page` of a copy matched `:last-child` (`break-after: auto`) and two copies ran together. `COPY_BREAK_CSS` is now exported and appended when batching, and a render integration test asserts "2 copies × 3 pages = 6 pages".
- `@worm-vue3-print/core`: The browser adapter `renderHtmlPages` (`@worm-vue3-print/core/browser`) now accepts `TemplateData | MultiPageTemplateData` (and an array `printData`), so multi-page templates can be rendered in the browser directly.

### Known limitations

- Page rotation in multi-page documents takes the **first page's** `outputRotation`. Paper dimensions are already forced equal, but the angle is not part of that consistency check yet; per-page rotation is left as a future extension.
- Multi-page templates do not support continuous paper or label tiling, nor data-driven conditional pages (for example appending a terms page only when an amount exceeds a threshold).
